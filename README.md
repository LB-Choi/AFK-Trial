# AFK Trial — 기능 구현 테스트 프로젝트

이 저장소는 정규 게임 제작물이 아니라 Unity에서 기능을 구현하고 확인하기 위한 테스트 프로젝트다. Universal 2D 기본 씬에서 실행되는 자동 전투 최소 기능과 개발 환경 설정을 포함한다. 현재는 사용자 지시에 따라 로컬에서만 작업하며 GitHub 연결·푸시는 진행하지 않는다.

## 테스트 실행

본 제작의 전투 방향은 좌우 대치다. `LOF/Assets/Scenes/SideBattle.unity`를 열고 Play하면 960×540 기준 왼쪽 아군과 오른쪽 적이 중앙으로 접근한다. 아군 세 명은 편성한 캐릭터의 대기 스프라이트를 사용하며, 체력바는 전장 양옆에 고정된다. 기존 상하 전투 비교용 씬은 `SampleScene`이다.

1. `LOF/Assets/Scenes/SideBattle.unity`를 열고 코드 임포트가 끝날 때까지 기다린다.
2. Unity Play 버튼을 누른다. 두 전투 씬에서 실행기가 자동 생성된다. 컴포넌트를 수동으로 붙일 필요가 없다.
3. Formation을 열고 슬롯과 캐릭터를 차례로 선택한다. 이미 편성된 캐릭터를 고르면 두 슬롯이 교환된다. Apply & restart battle을 누르면 선택한 세 명이 출전해 접근·공격하며 HP가 감소한다. 승리하면 보상 획득 후 다음 단계로 자동 진행한다.
4. `Team level +1`은 골드·경험치가 충분하면 활성화된다. 테스트 편의를 위한 팀 전체 성장으로, 정규 기획의 캐릭터별 성장 UI를 대신 구현한 것이 아니다. 화면의 Team Lv.와 Battle Lv.로 다음 전투 적용 시점을 비교한다.
5. `Test: force defeat`로 패배·파밍 전환을 확인한다. 파밍에서 다시 패배하면 하위 단계로 이동하며 최저 연습 단계에서 멈춘다.
6. `Retry`로 원래의 다음 도전 목표에 복귀한다. `Pause / Resume`은 테스트를 잠시 멈추는 버튼이다.

현재 포함: 캐릭터 10종과 3인 편성, 3대3 기본 공격, 최근접 대상 선택·사망까지 유지, 자동 이동, HP·공격 간격, 제한 시간, 동시 전멸 패배, 5단계마다 보스, 회차 표시, 일반/최초 재화 보상, 파밍, 성장·재도전.

현재 제외: 역할·시너지, 30개 스킬, 소환권·뽑기·장비, 던전, 저장·방치, 최종 아트·UI·밸런스. 임시 수치는 테스트용이며 진행도는 Play 종료 시 사라진다. UI는 기본 폰트 호환을 위해 영문이다.

## 게임 데이터 수정

원본 테이블은 `LOF/Assets/StreamingAssets/Data`에 있다. Excel에서 첫 행의 열 이름을 유지하고 **CSV UTF-8(쉼표로 분리)** 형식으로 저장한 뒤 Unity Play를 다시 시작하면 적용된다. 소수점은 마침표를 쓴다. Windows 빌드에서 수치만 시험할 때는 `AFK-Trial_Data/StreamingAssets/Data`의 복사본을 수정하고 게임을 다시 실행한다. 다음 빌드에도 유지할 변경은 프로젝트 원본에 반영한다.

| 파일 | 조정 항목 |
| --- | --- |
| Heroes.csv | 캐릭터별 이름, 초상화, 애니메이션, 기본 HP·공격력, 레벨당 증가량, 이동 속도, 사거리, 공격 주기(초), 초기 편성 |
| Enemies.csv | 일반 적과 보스의 이름, 기본 HP·공격력, 이동 속도, 사거리, 공격 주기(초) |
| Progression.csv | 보스 등장 간격과 위치, 회차 길이, 제한 시간, 적 스탯 배율, 보상, 레벨업 비용, 배치 간격, 전투 재시작 대기 시간 |
| HitFlash.csv | 타격 시트의 Resources 경로, 가로·세로 칸 수, 사용할 프레임 수, 초당 프레임, 가로·세로 화면에서의 표시 크기 |

예를 들어 Heroes.csv의 `ice_knight` 행에서 `hp`를 120, `attack`을 18로 저장하면 1레벨 얼음검 기사가 HP 120, 공격력 18로 시작한다. `startingSlot` 1~3은 각각 한 명에게 지정하고 대기 캐릭터는 0으로 둔다. 이름을 변경해도 리소스·애니메이션 연결은 유지된다. 스테이지의 적 배율은 기본 배율에 스테이지 번호와 단계당 증가량의 곱을 더한 값이다. 연습 스테이지에는 별도 배율을 적용한다.

신규 콘텐츠의 조정 가능한 게임 수치도 CSV에 추가한다. 개발 완료 시 테이블별 시트를 담은 Excel 파일을 출력하고, 각 시트를 같은 이름의 CSV로 저장해 게임에 반영한다.

타격 효과는 [ParticleFX Studio의 Hit Flash](https://particlefx.studio/effects/hit-flash) 무료 PNG 출력에서 예시 캐릭터를 제외하고 첫 번째 타격을 추출했다. 피해를 받은 유닛의 위치에서 한 번 재생한다.

### 확인 결과와 재실행

- Unity 6000.5.0f1에서 컴파일 후 모델 검사가 통과했다. 첫 승리·보상 중복 방지·성장 반영·파밍·후퇴·최저 단계·재도전·동시 전멸·재화 부족·회차 표기를 검사한다.
- `AFK Trial > Run Model Checks` 메뉴로 다시 실행할 수 있다. 상세 결과는 로컬 `LOF/Logs/TrialChecks.txt`에 기록한다. Logs는 Git 제외 대상이다.
- Editor 코드 재로드 때는 실제 CSV 구성을 검사한다. 메뉴에서 실행하는 모델 회귀 검사는 고정된 테스트용 데이터로 기존 전투 규칙을 확인한다.
- 가로 Windows 빌드는 `output/LandscapeTest/AFK-Trial.exe`로 실행한다. 실제 960×540 창에서 첫 스테이지와 양측 체력 패널을 확인했다. 화면 캡처는 `output/LandscapePreview.png`다. 이 캡처는 편성창 추가 이전 화면이다.

## 환경

- Unity: **6000.5.0f1** (프로젝트 버전 파일 기준)
- 프로젝트: 저장소 루트의 `LOF` 폴더, Universal 2D / URP
- IDE: Visual Studio 2022 또는 VS Code. IDE 선택은 각 PC의 Unity Preferences에서 설정한다.
- 테스트 출력: Windows, 가로 16:9. 기본 창 960×540, 크기 변경 허용.
- 현재 PC: RAM 32 GB / NVIDIA GeForce RTX 5070 Ti. 최소 요구 사양이나 고정 개발 조건이 아니다.
- 사용자 이름이나 `C:/Users/User`를 코드에 고정하지 않는다.

## 다른 PC에서 이어서 작업하기

1. GitHub 저장소를 복제하거나 작업 시작 전에 최신 커밋을 가져온다.
2. Unity Hub에서 정확히 `6000.5.0f1`을 설치하고 로그인·라이선스 활성화를 완료한다.
3. Hub에 `LOF` 폴더를 추가해 연다. `Library`와 패키지 캐시는 자동 재생성되며 인터넷이 필요할 수 있다.
4. 첫 임포트가 완료되면 Editor 전용 스크립트가 테스트 창 설정을 적용한다. Console의 `[AFK Trial] Test setup applied` 메시지로 확인한다. 수동 재적용 메뉴는 `AFK Trial > Apply Test Project Settings`다.
5. Game 뷰 비율은 각 PC에서 16:9로 선택한다. Windows 창 설정은 Game 뷰 비율을 자동 변경하지 않는다.
6. `HANDOFF.md`의 최신 상태를 확인하고 다음 작업을 이어간다.

선택: 저장소 루트에서 `powershell -File ./tools/Open-Unity.ps1`로 프로젝트를 열 수 있다. Unity가 다른 위치에 설치되어 있으면 `-EditorPath "D:/.../Unity.exe"`를 전달한다. 설치 버전 자체는 Hub에서 확인한다.

## Git 보관 기준

- 보관: `LOF/Assets`와 `.meta`, `LOF/Packages`의 manifest와 lock, `LOF/ProjectSettings`, 문서와 도구.
- 제외: Library, Temp, Logs, UserSettings, IDE 캐시, 생성된 솔루션과 빌드 출력.
- `.meta`와 해당 리소스는 함께 이동·커밋한다.
- 라이선스·인증 토큰은 저장소에 넣지 않는다. 로그인은 새 PC에서 진행한다.
- 현재 별도 대용량 아트가 없어 Git LFS는 적용하지 않았다. 추후 리소스 추가 전 용량을 확인한다.
- 플레이 세이브는 소스 관리 대상이 아니다. 별도 백업이 필요하면 정책을 정한다.

## 매일 작업 종료

1. Unity의 씬과 프로젝트 변경을 저장한다.
2. `git status --short`와 diff에서 변경을 확인한다.
3. 필요한 소스·설정·기록을 커밋한다.
4. 연결된 GitHub 원격에 푸시하고 성공 여부를 확인한다. 로컬 커밋만으로는 PC 초기화에 대비할 수 없다.
5. HANDOFF에 구현 범위, 실제 확인 결과, 남은 문제와 다음 시작점을 기록한다.

현재 원격 주소는 미연결이다. 사용자가 로컬 작업을 선택했으므로 원격 연결이나 업로드를 대기 작업으로 취급하지 않는다. PC 초기화 전 보존이 필요하면 별도 백업을 진행해야 한다.

## 테스트 개발 범위

후속 구현 순서는 기본형 Play Mode 확인 → 스킬·편성 → 뽑기·장비 → 저장·방치·던전이다. 각 기능의 임시 수치는 최종 밸런스와 구분한다. 모델 검사 통과는 최종 게임 완성이나 전체 QA 통과를 뜻하지 않는다.

Editor 설정 스크립트는 첫 임포트 시 `Library/AFKTrialSetup-v2.txt`에 실행 기록을 남긴다. Library를 재생성하면 테스트 설정이 다시 적용된다. `runInBackground=false`는 전체 최소화·방치 시스템의 구현을 대신하지 않는다.
